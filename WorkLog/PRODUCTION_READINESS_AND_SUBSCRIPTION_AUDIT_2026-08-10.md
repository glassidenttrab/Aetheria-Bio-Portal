## 1. 최종 결론

### 판정: 실제 유료 구독 서비스 출시 `NO-GO`

현재 시스템은 **UI 데모와 제한된 비결제 베타 서비스에는 사용할 수 있지만, 실제 결제를 받고 Pro/Enterprise 권한을 제공하는 상용 구독 서비스로 출시하면 안 된다.**

가장 큰 이유는 다음과 같다.

1. 결제 성공과 요금제 권한 부여를 브라우저가 결정한다.
2. 사용자가 자신의 `plan`과 `queries_remaining`을 DB에서 변경할 수 있는 구조다.
3. PayPal은 Sandbox의 1회성 결제이며 정기구독·웹훅·환불·취소·만료 처리가 없다.
4. 핵심 AI 분석 결과 대부분이 실제 외부 데이터 조회가 아닌 정적 데모 데이터다.
5. 신규 DB 스키마가 민감 테이블을 임시 전면 공개 정책으로 생성한다.
6. 공개 저장소 문서에 Google OAuth Client Secret이 기록되어 있다.

### 출시 형태별 판단

| 출시 형태 | 판단 | 조건 |
|---|---|---|
| 내부 시연 | 가능 | 데모 데이터임을 명시하고 실사용 개인정보를 넣지 않을 것 |
| 외부 무료 데모 | 조건부 가능 | RLS 적용 확인, 노출된 자격 증명 폐기, 허위·과장 문구 수정 후 |
| 제한된 무료 베타 | 조건부 가능 | 위 조치 + 모니터링, 이용약관 정비, 데이터 수집 최소화 |
| 실제 Pro/Enterprise 결제 | 불가 | 서버 검증 결제·권한·쿼터 구축 전 금지 |
| 바이오 의사결정용 분석 서비스 | 불가 | 실제 데이터 파이프라인, 출처·시점·한계·검증 체계 구축 전 금지 |

## 2. 현재 시스템의 실제 구조

현재 애플리케이션은 React 18, TypeScript, Vite 기반의 단일 페이지 프론트엔드다.

```text
사용자 브라우저
├─ React UI 및 8개국어 i18n
├─ Supabase JS → 인증과 DB CRUD 직접 수행
├─ PayPal JS SDK → 브라우저에서 주문 생성·캡처
├─ AlphaFold EBI API → 일부 3D 구조 조회
└─ 3Dmol.js → 단백질 구조 렌더링
```

`server/`에는 실행 가능한 API 서버가 없고 SQL 파일만 있다. 따라서 결제 검증, 웹훅, 권한 부여, 쿼터 차감, 외부 과학 API 통합을 신뢰할 수 있는 서버에서 처리하지 않는다.

Docker 구성도 nginx 정적 웹과 PostgreSQL을 함께 실행하지만, 실제 앱은 컨테이너 PostgreSQL이 아니라 Supabase에 직접 연결한다. 현재 Compose의 DB는 애플리케이션 실행 경로와 분리되어 있다.

## 5. 출시 차단 이슈

### P0-1. 공개 문서에 OAuth Client Secret 포함

`오픈계획서.md`에 Google OAuth Client ID와 Client Secret이 평문으로 기록되어 있다. 공개 저장소의 Git 이력에 들어간 비밀값은 파일에서 삭제하는 것만으로 안전해지지 않는다.

필수 조치:

1. Google Cloud Console에서 해당 Client Secret을 즉시 폐기하고 재발급한다.
2. Supabase Google Provider에도 새 Secret을 등록한다.
3. 문서와 현재 파일에서 실제 값을 제거한다.
4. 필요하면 Git 이력 정리를 수행하되, 이력 정리 여부와 관계없이 기존 Secret은 영구 폐기한다.
5. 저장소 비밀 탐지 CI를 추가한다.

### P0-2. 신규 DB 설치 시 전면 공개 RLS

`server/db/schema.sql`은 `users`, `subscriptions`, `api_keys`, `skill_audit_logs`에 `FOR ALL USING (true)` 정책을 만든다. `rls_hardening_migration.sql`을 별도로 실행하지 않은 환경에서는 anon key로 전체 데이터 읽기·수정·삭제가 가능할 수 있다.

필수 조치:

- 기본 스키마를 처음부터 deny-by-default 정책으로 변경한다.
- 운영 Supabase에서 실제 적용된 정책을 SQL로 조회하고 증빙을 남긴다.
- 공개 정책이 하나라도 존재하면 실사용 데이터 입력과 외부 공개를 중지한다.
- SQL Editor 수동 실행이 아니라 버전 관리되는 Supabase Migration으로 전환한다.

### P0-3. 사용자가 유료 권한을 스스로 변경 가능

강화 RLS도 본인의 `users` 행 UPDATE를 허용하며, `is_admin` 상승만 막는다. `plan`과 `queries_remaining` 변경은 막지 않는다. 인증 사용자는 Supabase REST 호출로 자신을 Enterprise로 만들거나 쿼터를 복구할 수 있다.

필수 조치:

- 일반 사용자의 `plan`, `queries_remaining`, 결제 관련 필드 직접 UPDATE를 금지한다.
- 권한 부여는 서버의 서비스 역할 또는 제한된 `SECURITY DEFINER` 함수만 수행한다.
- 프로필 수정 가능 필드와 운영 전용 필드를 분리한다.

### P0-4. 결제 결과를 클라이언트가 신뢰

PayPal `onApprove` 이후 브라우저에서 바로 플랜을 변경하고 구독 행을 기록한다. 서버가 PayPal 거래 ID, 금액, 통화, 수취인, 상태를 재검증하지 않는다.

필수 조치:

- Supabase Edge Function 또는 별도 API 서버를 구축한다.
- 서버에서 PayPal API로 거래를 검증한 후에만 권한을 부여한다.
- PayPal Subscriptions API 또는 적절한 정기결제 상품을 사용한다.
- 서명 검증 웹훅으로 활성화·갱신·취소·환불·분쟁·연체를 동기화한다.
- PayPal 이벤트 ID 기반 멱등성을 적용한다.

### P0-5. 쿼터가 localStorage와 클라이언트 상태에 의존

무료 3회, Pro 30회, Enterprise 500회의 쿼터는 브라우저 localStorage의 기간 값과 수정 가능한 DB 필드에 의존한다. 사용자가 저장소를 지우거나 직접 값을 바꾸면 우회할 수 있다.

필수 조치:

- 서버 시간 기준의 원자적 쿼터 차감 RPC를 구현한다.
- 분석 작업 생성과 쿼터 차감을 하나의 트랜잭션으로 묶는다.
- 사용자·IP·API 키 단위 Rate Limit을 추가한다.
- 실패한 분석의 환급 정책과 중복 요청 방지 키를 정의한다.

### P0-6. 핵심 상품 가치가 정적 데모 데이터

유료 플랜의 핵심 가치로 보이는 분석 결과가 실제 PubMed, ChEMBL, OpenTargets, ClinicalTrials 등의 조회 결과가 아니다. 특히 모든 타깃에 유리한 FTO 판정을 표시하면 사용자의 연구·사업 판단을 왜곡할 수 있다.

필수 조치:

- 실제 연동 전에는 모든 분석 화면에 `데모/예시 데이터`를 명확히 표시한다.
- "라이브", "통합 완료", "Clear FTO" 등 검증되지 않은 문구를 제거한다.
- 결과마다 데이터 출처, 조회 시각, 원문 링크, 버전, 한계와 면책을 표시한다.
- FTO 결과는 법률 자문이 아니며 자동 확정 판정이 아님을 명시한다.

## 6. 높은 우선순위의 부족한 부분

### 인증과 관리자 권한

- 관리자 화면 진입은 번들에 공개되는 `VITE_ADMIN_EMAILS`를 사용한다.
- 실제 DB 권한은 `users.is_admin`에 의존해 UI와 권한의 기준이 분리되어 있다.
- 관리자 기능은 서버에서 역할을 검증하도록 통합해야 한다.
- 회원가입 남용 방지를 위한 이메일 확인, CAPTCHA 또는 위험 기반 제한이 필요하다.

### API 키

- `api_key_hash`라는 컬럼에 실제 키 문자열을 저장하고 다시 화면에 표시한다.
- 키는 생성 시 한 번만 보여주고 DB에는 단방향 해시만 저장해야 한다.
- 만료, 폐기, 회전, 범위(scope), 마지막 사용 시각, 감사 로그가 필요하다.

### 개인정보와 규정

- GDPR/CCPA 준수를 표현하지만 데이터 열람·내보내기·삭제 절차가 구현되어 있지 않다.
- 쿠키·분석 도구 동의 관리, 보존 기간, 처리 위탁자 목록, 침해 대응 절차가 없다.
- 바이오 연구 데이터와 개인정보를 받을 경우 민감도 분류와 최소 수집 정책이 필요하다.
- 의료기기 또는 진단 서비스로 오인되지 않도록 서비스 범위를 명확히 해야 한다.

### 운영 안정성

- GitHub Actions 등 CI가 없다.
- DB 마이그레이션 자동화, 백업, 복구 훈련, 장애 대응 Runbook이 없다.
- nginx에 CSP, HSTS, frame 제한, MIME 보호 등의 보안 헤더가 없다.
- Sentry는 선택적 설정만 있고 알림·담당자·대응 기준을 확인할 수 없다.
- 지원은 개인 Gmail의 `mailto:` 중심이며 티켓, SLA, 상태 페이지가 없다.

### 접근성과 성능

- 모달의 `role="dialog"`, `aria-modal`, 포커스 트랩, ESC 종료, 포커스 복원이 부족하다.
- 단일 JS 번들이 1.52MB, gzip 425.98KB로 크다.
- 3Dmol, PayPal, 관리자·Enterprise 화면을 동적 import로 분리해야 한다.

## 7. 테스트 및 빌드 실측 결과

2026년 8월 10일 로컬 환경에서 다음을 직접 실행했다.

| 명령 | 결과 |
|---|---|
| `npm run test` | 성공: 테스트 파일 2개, 테스트 7개 모두 통과 |
| `npm run lint` | 종료 코드 0, 오류 0개, 경고 57개 |
| `npm run build` | 성공 |
| `npm audit --json` | 취약점 2개: High 1개, Moderate 1개 |

빌드 결과:

- JavaScript: 1,520.79KB
- gzip: 425.98KB
- Vite의 500KB 초과 청크 경고 발생
- 3Dmol의 `eval` 사용 경고 발생

해석:

- 컴파일과 현재 단위 테스트는 통과하지만 테스트 범위가 매우 작다.
- 인증, RLS, 결제, 웹훅, 플랜 변경, 관리자 권한, DB 오류, E2E 테스트가 없다.
- lint 경고가 배포를 차단하지 않아 죽은 코드와 Hook 의존성 문제가 누적되어 있다.
- Vite 5 계열 개발 서버 관련 알려진 취약점이 있으므로 호환성 검증 후 업그레이드해야 한다.

## 8. 권장 목표 아키텍처

```text
브라우저
  └─ 인증된 요청
      ↓
Supabase Edge Functions 또는 별도 API
  ├─ PayPal API 검증 및 웹훅
  ├─ 플랜·권한·쿼터 원자적 변경
  ├─ 입력 검증과 Rate Limit
  ├─ 과학 데이터 API 통합
  ├─ 캐시와 작업 큐
  └─ 감사 로그·관측성
      ↓
Supabase PostgreSQL
  ├─ 기본 차단 RLS
  ├─ 사용자 프로필 필드와 운영 필드 분리
  ├─ 결제 이벤트 멱등성
  └─ 분석 결과의 출처·버전·조회 시각 저장
```

초기 실제 분석 MVP는 `.agents/skills/`의 자료를 바탕으로 UniProt, PubMed/Europe PMC, ChEMBL, OpenTargets 3~4개를 우선 연결하는 것이 적절하다. 다만 외부 API의 이용약관, 상업적 사용 제한, Rate Limit, 데이터 재배포 조건을 각각 확인해야 한다.

## 9. 단계별 개선 계획

### Phase 0 — 즉시, 외부 공개 전

- 노출된 Google OAuth Client Secret 폐기·재발급
- 운영 Supabase RLS 실제 상태 확인 및 전면 공개 정책 제거
- `오픈계획서.md`의 비밀값과 과장된 완료 표시 제거
- 모든 정적 분석 결과에 데모 라벨 표시
- Supabase URL·anon key 하드코딩 fallback 제거
- Docker Compose의 고정 DB 비밀번호 제거

### Phase 1 — 유료 결제 개발

- PayPal 정기구독 또는 대체 Billing 도입
- 결제 검증 API와 서명 검증 웹훅 구현
- 서버 전용 플랜 부여와 구독 상태 머신 구현
- 서버 측 원자적 쿼터 차감과 Rate Limit 구현
- 사용자 프로필과 entitlement 필드 권한 분리
- 결제 이벤트·환불·분쟁·취소 감사 로그 구현

### Phase 2 — 실제 분석 MVP

- 우선순위 과학 API 3~4종 서버 통합
- 타임아웃, 재시도, 캐시, 데이터 출처와 버전 기록
- 외부 API 장애 시 부분 결과와 오류를 정직하게 표시
- FTO와 의학적 결과의 검토·면책·품질 기준 수립

### Phase 3 — 출시 품질

- GitHub Actions에 install, test, lint, build, audit, secret scan 추가
- 결제·RLS·권한 통합 테스트와 Playwright E2E 추가
- 접근성 WCAG 2.1 AA 핵심 항목 개선
- 코드 스플리팅과 성능 예산 적용
- Sentry 알림, 상태 페이지, 백업·복구, 장애 대응 문서화
- 개인정보 처리, 환불, 정기결제, 해지 정책을 실제 동작과 일치시킴

## 10. 유료 출시 승인 기준

다음 항목이 모두 충족되기 전에는 실제 결제를 활성화하지 않는다.

- [ ] 노출된 OAuth Secret 폐기 및 새 Secret 적용 확인
- [ ] 운영 DB에 전면 공개 RLS 정책이 없음을 SQL 결과로 확인
- [ ] 일반 사용자의 `plan`·`queries_remaining` 직접 변경 차단
- [ ] PayPal 거래 서버 검증 및 서명 검증 웹훅 운영
- [ ] 취소·환불·분쟁·만료 시 권한 회수 자동화
- [ ] 서버 측 원자적 쿼터 차감과 Rate Limit 적용
- [ ] 결제·권한·RLS 공격 시나리오 테스트 통과
- [ ] 핵심 분석이 실제 데이터이거나 데모임을 오인 불가하게 표시
- [ ] 마케팅, 가격, 쿼터, 약관의 표현이 코드와 일치
- [ ] CI에서 테스트·lint·build·secret scan 필수 통과
- [ ] 운영 모니터링, 백업·복구, 장애 대응 담당자와 절차 확정
- [ ] 개인정보 삭제·내보내기·보존 절차 확정

## 11. 긍정적인 기반

현재 상태가 상용 출시 가능하다는 뜻은 아니지만, 다음 기반은 재사용 가치가 높다.

- 프론트엔드와 다국어 UI의 완성도가 높다.
- Supabase Auth와 사용자 프로필 저장 경로가 마련되어 있다.
- RLS 강화 마이그레이션 초안이 있어 재설계 출발점으로 사용할 수 있다.
- 실제 AlphaFold API 사용 경험이 코드에 반영되어 있다.
- Error Boundary, Sentry, Vitest, ESLint, Docker 배포 골격이 있다.
- `.agents/skills/`에 과학 데이터 API 조사 자료가 축적되어 있다.
- README가 핵심 분석 엔진이 데모 상태임을 비교적 정직하게 명시한다.

따라서 전체 재개발보다는 **신뢰 경계를 브라우저에서 서버로 이동하고, 실제 데이터 파이프라인을 단계적으로 연결하는 방식**이 적절하다.

## 12. 최종 권고

현재 서비스는 **“상용 UI 수준의 바이오 SaaS 프론트엔드 프로토타입”**으로 정의하는 것이 정확하다.

외부 시연은 가능하지만 실제 결제 버튼은 Sandbox 상태로 유지하고, 분석 결과에는 데모 표시를 해야 한다. 유료 출시의 첫 번째 개발 목표는 화면 추가가 아니라 다음 세 가지여야 한다.

1. 서버에서 검증되는 결제와 권한
2. 서버에서 강제되는 쿼터와 RLS
3. 출처가 추적되는 실제 과학 데이터

이 세 가지가 완료되기 전 실제 구독을 시작하면 무단 Enterprise 권한 획득, 데이터 노출, 결제 분쟁, 과장 광고 및 연구 판단 오류 위험을 감수하게 된다.

## 1. 한 줄 결론

**보안이 약해서 위험한 게 아니라, 구독 상품 자체가 코드에 구현되어 있지 않다.**

지금 결제 버튼을 실제 운영 모드로 바꾸면 시스템은 "월 구독"이 아니라 **"1회 결제 후 영구 이용권"**을 판매하게 된다. 이건 설정 실수가 아니라 갱신·만료·강등 로직이 코드에 존재하지 않기 때문에 생기는 구조적 결과다.

## 2. 상업적으로 치명적인 문제 5가지

### 2.1 월 구독이 실제로는 평생 이용권이다

`plan`을 올리는 코드는 있지만 내리는 코드가 저장소 전체에 없다.

- `handlePaymentSuccess`(`src/App.tsx:152`)가 `plan`을 올린다.
- `recordSubscriptionDB`(`src/services/supabaseService.ts:158`)는 `status: 'active'`와 `started_at`만 기록한다.
- `expires_at`은 `supabaseService.ts:261`의 타입 정의에만 존재하고, **어디서도 값을 넣지 않고 어디서도 검사하지 않는다.**
- 구독 만료·해지·결제 실패로 권한을 회수하는 경로가 전무하다.

결과: 사용자가 $490을 **한 번** 결제하면 Pro 권한이 영구히 유지된다. 2개월차부터는 청구도 없고 회수도 없다. 매출 예측이 성립하지 않는다.

### 2.2 쿼터가 계정이 아니라 브라우저에 붙어 있다

`resolveQuota`(`src/utils/quota.ts:31`)는 localStorage에 저장된 기간 문자열이 현재 기간과 다르면 무조건 플랜 한도로 리셋한다. 저장된 값이 없으면(`null`) 당연히 다르므로 즉시 리셋된다.

즉 다음 상황에서 쿼터가 전부 복구된다.

- 시크릿 창으로 접속
- 다른 브라우저나 다른 PC로 접속
- 브라우저 사이트 데이터 삭제

개발자 도구를 열 필요도, 악의도 필요 없다. **Pro 월 30회, Enterprise 월 500회 한도는 사실상 존재하지 않는다.** 게다가 리셋 값이 `onUpdateUser`를 통해 DB에도 기록되므로(`src/components/SaaSPlatformView.tsx:63-69`), 브라우저를 옮겨다니는 것만으로 서버 값까지 계속 되살아난다.

### 2.3 로그인하지 않아도 결제 버튼이 눌린다

`SubscriptionCheckoutModal`은 비로그인 사용자에게 "로그인이 필요합니다" 안내 배너만 보여주고(`:174`), **PayPal 버튼은 조건 없이 그대로 렌더링한다**(`:327-334`).

여기에 `/checkout` 딥링크가 인증 확인 없이 결제 모달을 자동으로 연다(`src/App.tsx:114`).

비로그인 상태에서 결제가 성공하면 `handlePaymentSuccess`가 `user.email`(게스트는 빈 문자열)로 `recordSubscriptionDB`를 호출한다. 돈은 PayPal에서 빠져나가지만 붙일 계정이 없다. **결제는 됐는데 아무 권한도 못 받는 사용자**가 생기고, 이건 그대로 환불 분쟁이다.

### 2.4 표시 가격과 청구 가격이 다르다

Enterprise 가격이 화면마다 다르다.

- 실제 청구액: `$2,500` (`SubscriptionCheckoutModal.tsx:19`)
- 안내 문구: `$1,990/월` (`SaaSPlatformView.tsx:79`, `MyResearchPortalView.tsx:60`, `:225`)

사용자가 `$1,990` 안내를 보고 진입해 `$2,500`을 청구받는 경로가 실재한다. 금액 차이가 큰 만큼 단순 오타가 아니라 결제 분쟁과 표시광고 문제로 직결된다.

### 2.5 일할 정산이 항상 20일로 고정되어 있다

`SubscriptionCheckoutModal.tsx:68`의 `proDaysRemaining = 20`은 상수다. 실제 구독 시작일을 보지 않는다.

따라서 Pro 구독 29일차에 Enterprise로 업그레이드해도 미사용 20일치인 `$326.67`을 그대로 크레딧으로 깎아준다. 반대로 방금 결제한 사용자는 손해를 본다. 어느 쪽이든 정산 근거가 없고, 화면에는 "정확히 일할 계산되어 차감 승인됩니다"(`:308`)라고 표시된다.

추가로 연간 결제는 `$4,998`을 1회 캡처로 받는데, 약관에는 "월 단위 자동 갱신"과 "7일 내 미사용 시 전액 환불"이 명시되어 있다(`PrivacyTermsModal.tsx:186`). 구현과 약관이 서로 다른 상품을 설명하고 있다.

## 3. 가장 주목할 구조적 문제: RLS 딜레마

이 부분은 "정책을 적용하면 안전해진다"로 정리할 수 없다. 적용해도 문제가 생긴다.

`rls_hardening_migration.sql`의 정책은 소유자를 `user_id`로 판정한다.

```sql
CREATE POLICY "subscriptions_insert_own_or_admin" ON public.subscriptions
  FOR INSERT WITH CHECK (
    public.is_current_user_admin()
    OR user_id IN (SELECT id FROM public.users WHERE auth_uid = auth.uid()::text)
  );
```

그런데 애플리케이션 코드는 `user_id`를 넣지 않는다.

- `recordSubscriptionDB`의 insert에 `user_id` 없음 (`supabaseService.ts:170-179`)
- `saveSkillAuditLogDB`의 insert에 `user_id` 없음 (`supabaseService.ts:114-123`)

`user_id`가 NULL이면 `NULL IN (...)`은 참이 되지 않으므로 WITH CHECK를 통과하지 못한다. `skill_audit_logs`의 `FOR ALL USING (...)` 정책도 WITH CHECK가 생략되어 있어 INSERT에는 USING 식이 그대로 적용된다. 두 insert 모두 거부된다. 그런데 코드는 오류를 `console.warn`으로 삼키고 호출부는 반환값을 확인하지 않는다.

정리하면 현재 운영 DB는 둘 중 하나다.

| 상태 | 결과 |
|---|---|
| 강화 정책 미적용 | anon 키만으로 회원·구독·API 키 테이블 전체 접근 가능 |
| 강화 정책 적용 | 결제 기록과 감사 로그가 조용히 저장되지 않음 |

두 경우 모두 유료 서비스를 운영할 수 없는 상태다. **어느 쪽인지부터 확인하는 것이 가장 먼저 할 일이다.** 최근 커밋이 "감사 로그가 0으로 보여서 고쳤다"는 취지인 점을 보면, 실제로는 강화 정책이 아직 적용되지 않았을 가능성이 높다.

### 3.1 파생 문제: 신원 키가 두 개다

애플리케이션은 사용자를 `email`로 찾고(`fetchUserProfileDB`), `onConflict: 'email'`로 upsert한다. 반면 RLS는 `auth_uid`로 판정한다. 기준이 두 개다.

여기에 회원가입 정책이 `FOR INSERT WITH CHECK (true)`라 **누구나 임의 이메일로 users 행을 미리 만들 수 있다.** 선점당한 이메일의 실제 주인이 나중에 가입하면, 조회는 `auth_uid` 불일치로 0건이 되고, 앱은 신규 가입으로 판단해 프로필 생성을 시도하며, 이메일 충돌로 UPDATE로 전환되지만 그 UPDATE 역시 `auth_uid` 불일치로 막힌다. 정상 가입자가 자기 프로필을 영구히 저장하지 못하는 상태가 된다.

## 4. 제품 신뢰 측면

`neuroLongevityEngine.ts`의 분석 결과가 정적 데이터라는 점은 이미 알려진 사실이지만, 유료 관점에서 다시 보면 문제의 성격이 다르다.

- Pro 플랜의 판매 문구가 "AI 정밀 타깃 분석 및 FTO 특허 리포트"(`SubscriptionCheckoutModal.tsx:58`)다. 즉 **정적 데이터가 곧 과금 대상 기능**이다.
- 모든 타깃의 FTO 판정이 예외 없이 유리하게 고정되어 있다. 무료 데모라면 과장이지만, 유료 리포트라면 구매자의 사업 판단을 왜곡하는 정보다.
- Enterprise 설명은 "무제한 38+ 스킬"인데 실제 상한은 월 500회다.

결제를 붙이는 순간 이 항목들의 성격이 마케팅 과장에서 계약 불이행 쪽으로 이동한다.

## 5. 출시 형태별 판단

| 형태 | 판단 | 근거 |
|---|---|---|
| 내부 시연 | 가능 | 결제 미개통이면 위 항목 대부분 무해 |
| 무료 데모 공개 | 조건부 가능 | RLS 상태 확인, 노출된 OAuth Secret 폐기, 분석 결과에 데모 표기 |

| 유료 구독 개시 | **불가** | 갱신·만료·회수·쿼터·결제 검증이 코드에 없음 |

## 6. 유료화를 목표로 할 때의 최소 작업 순서

정확히 이 순서를 권한다. 앞 단계를 건너뛰면 뒷 단계가 의미가 없다.

1. **운영 DB의 현재 RLS 정책을 조회해 상태를 확정한다.** 이것부터 확인해야 나머지 판단이 가능하다.
2. **노출된 Google OAuth Client Secret을 폐기·재발급한다.** 문서에서 지우는 것만으로는 해결되지 않는다.
3. **비로그인 결제 경로를 막는다.** PayPal 버튼을 로그인 상태에서만 렌더링한다. 코드 몇 줄이지만 실제 금전 사고를 막는다.
4. **가격 표기를 하나로 통일한다.** `$1,990`을 전부 제거한다.
5. **결제 검증 서버를 만든다.** PayPal 거래 ID·금액·통화·상태를 서버에서 재확인한 뒤에만 권한을 부여한다.
6. **구독 상태 모델을 만든다.** `expires_at`, 갱신, 해지, 실패, 회수까지 상태 전이를 정의하고 웹훅으로 동기화한다.
7. **쿼터를 서버에서 원자적으로 차감한다.** localStorage 리셋 로직은 제거한다.
8. **RLS와 애플리케이션의 신원 키를 `auth_uid`로 통일하고**, insert 시 `user_id`를 채우며, DB 오류를 삼키지 않도록 바꾼다.
9. **분석 결과의 데모 표기 또는 실제 데이터 연동**을 결제 개시 전에 끝낸다.

1번부터 4번까지는 하루 안에 가능하고, 5~8번이 실질적인 개발 과제다.

## 7. 평가에서 조정하고 싶은 부분

같은 날 작성된 감사 보고서와 비교해 제 판단이 다른 지점을 남긴다.

- **"보안 취약"보다 "상품 미구현"이 정확한 표현이다.** RLS를 완벽히 조여도 만료 로직이 없으면 구독 사업은 성립하지 않는다.
- **쿼터 우회는 공격이 아니라 기본 동작이다.** 악의적 사용자가 아니라 브라우저를 바꾼 일반 사용자에게도 발생한다.
- **RLS 강화는 그 자체로 안전 조치가 아니다.** 현재 코드 상태에서 적용하면 결제 기록이 사라지므로, 코드 수정과 반드시 함께 가야 한다.
- **긍정적으로 볼 부분은 분명하다.** 인증, 프로필, 보관함, 다국어, 일부 AlphaFold 연동, 빌드·배포 골격은 재사용 가능하다. 문제는 프론트엔드 품질이 아니라 신뢰 경계가 전부 브라우저 안에 있다는 점 하나로 수렴한다.
